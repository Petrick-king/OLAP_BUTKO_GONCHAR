# Ключи и партиции `fact_sales` — как они помогают типичным фильтрам


---

## 1. Три разных рычага, которые часто путают в один

| Рычаг | В нашем DDL | На что влияет |
|-------|-------------|---------------|
| `PARTITION BY` | `toYYYYMM(order_date_key)` | на какие **папки на диске** разрезана таблица |
| `ORDER BY` | `(order_date_key, order_status, seller_id, …)` | **порядок строк внутри папки** и разреженный первичный индекс |
| `PRIMARY KEY` | не задан отдельно → совпадает с `ORDER BY` | по каким полям строится индекс гранул |

Бытовая аналогия: таблица — это шкаф, партиция — полка, `ORDER BY` — порядок
карточек на полке, `PRIMARY KEY` — оглавление к этим карточкам.

**`ORDER BY` — не уникальный ключ.** Две строки с одинаковым набором значений
в `ORDER BY` не запрещены и не схлопываются: ClickHouse просто положит их
рядом. Уникальность — это ограничение OLTP-базы (Postgres), а здесь её нет
ни в каком виде. Дедупликацию даёт отдельный движок (`ReplacingMergeTree`),
и то — при слиянии частей, а не в момент вставки.

## 2. Как это работает на нашем главном фильтре

Типичный вопрос паспорта: «оборот за период». Значит в `WHERE` всегда есть
`order_date_key`, часто рядом `order_status = 'delivered'`.

Порядок в `ORDER BY` выбран так, чтобы эти два поля шли **первыми**:

```sql
ORDER BY (order_date_key, order_status, seller_id, category_name_pt,
          customer_id, product_id, order_id, order_item_id)
```

Дальше — ключи джойнов в порядке частоты фильтрации, в конце — зерно строки
(`order_id`, `order_item_id`), чтобы одинаковые заказы лежали рядом.

### Что видно в плане

Запрос «сумма за один день 2018-01-15 по доставленным»:

```
MinMax      Parts: 1/26    Granules: 2/29     ← отсечены 25 частей из 26
Partition   Parts: 1/1     Granules: 2/2      ← внутри месяца — он один
PrimaryKey  Parts: 1/1     Granules: 1/2      ← из двух гранул прочитана одна
```

Читается это так:

1. **`MinMax` по `order_date_key`** — у каждой части хранится минимум и максимум
   даты. Если `2018-01-15` в интервал не попадает, часть не открывается вообще.
   25 частей из 26 отброшены, ни один байт из них не прочитан.
2. **`Partition` по `toYYYYMM(order_date_key)`** — то же самое, но на уровне
   партиций: остался ровно месяц `201801`.
3. **`PrimaryKey` по `(order_date_key, order_status)`** — внутри месяца
   оглавление гранул позволяет пропустить гранулу, где нужных строк нет.

Итого: вместо 29 гранул читается 1. Это не «ускорение в 100 раз» на учебном
объёме (112 650 строк), а **механизм**: он масштабируется сам, когда строк
станет в тысячу раз больше.

### Контрольный запрос без даты

Тот же запрос, но только с `order_status = 'delivered'`:

```
MinMax      Parts: 26/26   Granules: 29/29   ← читаем всё
Partition   Parts: 26/26   Granules: 29/29   ← партиции бесполезны
PrimaryKey  Parts: 23/26   Granules: 26/29   ← но 3 части отсеклись по статусу
```

Здесь видно главное ограничение: **партиция помогает только тогда, когда в
запросе есть условие по её ключу**. Фильтра по дате нет — все 24 месяца
читаются целиком. Зато `order_status` стоит вторым в `ORDER BY` и всё равно
отсёк 3 части: в них нет ни одной доставленной строки. Это три крошечные
части на одну дату — две в `201609` и одна в `201809`, по 1–2 строки.

## 3. Почему партиция по месяцу, а не по дню и не по году

| Вариант | Что было бы |
|---------|-------------|
| по дню | 600+ партиций на 112 650 строк — по 190 строк в каждой. Накладные расходы на части больше, чем экономия |
| по году | 3 партиции. Запрос «за январь 2018» читал бы весь 2018 год |
| **по месяцу** | **24 партиции; месяцы без данных просто не создаются** — компромисс |

Месяц выбран потому, что все вопросы паспорта формулируются в месяцах и
кварталах: «оборот 2017 года», «динамика по месяцам». Квартал тоже был бы
уместен, но месяц даёт более мелкое зерно удаления — а `PARTITION BY`
нужен ещё и для `TTL`/`DROP PARTITION`, когда данные станут старыми.

На учебном объёме (~40 МБ) партиция не даёт заметной скорости. Она взята
как **задел на рост**, и это честно записано в
[`../../07_З07_загрузка_clickhouse/notes/order_by.md`](../../07_З07_загрузка_clickhouse/notes/order_by.md).

## 4. Чего эти ключи не делают

| Ожидание | Реальность |
|----------|-----------|
| «`ORDER BY` запретит дубли» | нет: дубли лягут рядом, но останутся |
| «Запрос по `product_id` будет быстрым» | `product_id` шестой в ключе — индекс по нему не работает, будет чтение гранул |
| «Партиция ускорит любой запрос» | только тот, где есть фильтр по `order_date_key` |
| «Чем больше полей в `ORDER BY`, тем лучше» | чем длиннее ключ, тем крупнее оглавление и тем меньше строк в грануле; первые 1–3 поля дают почти весь эффект |

🤓 Отсюда практический вывод для дашборда З10: все виджеты фильтруются по
периоду, поэтому попадают в первый ключ. Виджет «топ категорий за год»
тоже получает выигрыш — по дате отсекаются лишние месяцы, а `category_name_pt`
читается уже внутри оставшихся гранул.
