# З09 — какой график и что означает одна строка сводки


## 1. Какой виджет будет на З10

**«Оборот доставленных заказов по дням и категориям товаров».**

График — линия по дням, цвет — категория (или столбики по дням для выбранной
категории). На дашборде к нему прилагается фильтр «период».

Почему именно он:

| Критерий | Как выполнено |
|----------|---------------|
| Нужен в паспорте | вопрос 2 паспорта — «топ категорий и их доля оборота»; график по дням — его детализация |
| Данные есть | `category_name_pt` денормализована в факт на З03, джойн не нужен |
| Фильтр по периоду | попадает в первый ключ `ORDER BY` факта (`order_date_key`) |
| Не «сводка вообще» | у неё ровно один разрез: день × категория |

## 2. Что означает одна строка сводки

> **Одна строка `mv_gmv_day_category` = один день × одна категория товара.**

Формально: строка существует, если в этот день были доставленные позиции
этой категории. Ключ строки — пара `(order_date_key, category_name_pt)`.

**Это не то же самое, что одна строка факта.**

| | Одна строка **факта** | Одна строка **сводки** |
|---|---|---|
| Что это | одна позиция одного заказа | один день × одна категория |
| Сколько строк | 112 650 | **18 808** |
| Можно ли сложить `amount` | да | да (уже сложен) |
| Можно ли сложить `orders` | нет (заказ может идти через несколько продавцов) | не хранится вовсе |
| Кто читает | аналитик, SQL | дашборд, ежесекундно |

Коэффициент схлопывания: **6.0×** (112 650 → 18 808).

## 3. Какие суммы лежат в строке

| Колонка | Тип | Определение | Аддитивна? |
|---------|-----|-------------|:----------:|
| `gmv_brl` | `Decimal(38,2)` | `SUM(amount)` по `status = 'delivered'` | да |
| `freight_brl` | `Decimal(38,2)` | `SUM(freight_value)` | да |
| `qty` | `UInt64` | `SUM(qty)` | да |
| `positions` | `UInt64` | `COUNT(*)` строк факта | да |

> **`orders` в сводке сознательно нет.** Заказ может содержать позиции
> разных категорий, поэтому `COUNT(DISTINCT order_id)` по строкам сводки
> не складывается: одна и та же пара день-заказ попадёт в несколько
> категорий, и сумма по категориям даст больше, чем заказов на самом деле.
> Это уже разобрано в З04 §1 (там же — 43 621 против 43 428).
> Если понадобится «заказов в дне» — это отдельная сводка с разрезом
> **только по дню**, без категории.

**Метрика та же.**

## 4. Почему `AggregatingMergeTree`, а не «просто таблица»

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| Обычная `MergeTree` + `INSERT ... SELECT` | просто, читается как есть | нет автоматики: забудешь пересобрать — сводка врёт |
| `SummingMergeTree` | складывает при слиянии | до слияния отдаёт дубли; дашборд обязан ставить `FINAL` или `GROUP BY` |
| **`AggregatingMergeTree` + `SimpleAggregateFunction`** | тип колонки сам говорит «это сумма»; точная семантика; `sum()` работает без комбинаторов | нужно помнить, что до слияния одна пара день×категория может лежать в двух частях |
| `AggregateFunction` + `sumState/sumMerge` | канонический способ | дашборд обязан писать `sumMerge(...)`, иначе получит бинарный state |

Выбран третий: он даёт и автоматику (view наполняет), и читаемость
(`sum(gmv_brl)` вместо `sumMerge(gmv_brl_state)`).

> **`Decimal(38,2)`, а не `Decimal(18,2)`.** `sum(Decimal(12,2))` в ClickHouse
> возвращает `Decimal(38,2)`, а `SimpleAggregateFunction` требует, чтобы тип
> хранения совпал с типом возврата. Это не «деньги стали шире» — точность
> после запятой та же, 2 знака.

## 5. Как пересобрать после повторной загрузки

**Одна команда:**

```bash
python 09_З09_mv_витрина/etl/build_mv.py
```

Она делает `TRUNCATE` сводки и заливает её заново из факта.

**Почему не «пусть view сама».** Загрузка факта в проекте — полный refresh
(`TRUNCATE fact_sales` + `INSERT`, см. З07). Materialized view реагирует на
каждую вставку и **не знает про удаление**: после перезагрузки в сводке
лежали бы и старые, и новые строки — двойной счёт.

Поэтому правило простое:

```
load_clickhouse.py  →  build_mv.py  →  дашборд
```

И ещё одно следствие, которое всплыло на проверке
([`../evidence/mv_fires_raw.txt`](../evidence/mv_fires_raw.txt)):
**на `DELETE` view не реагирует тоже.** Удалили строку из факта — из сводки
она не исчезнет, пока не пересоберёшь.

## 6. Что сводка не умеет

| Вопрос | Ответ |
|--------|-------|
| «Сколько заказов в дне?» | сводка не ответит: заказ не входит в её ключ |
| «Оборот по продавцам?» | нет: разрез фиксирован — категория |
| «Оборот по всем статусам?» | нет: в сводку попадают только `delivered` |
| «Средний чек?» | нет: `amount / orders` не собрать, потому что `orders` не хранится |

Это не недостатки, а **границы инструмента**: сводка отвечает на один
вопрос быстро. Для остальных есть факт и `canonical_metric.sql`.
