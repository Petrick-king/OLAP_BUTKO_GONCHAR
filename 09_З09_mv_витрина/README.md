## Что получилось

Собрана сводка `olist.mv_gmv_day_category` под график
**«оборот по дням и категориям»**.

> **Одна строка сводки = один день × одна категория товара.**
> В строке — уже готовая сумма оборота, а не позиция чека.

| Показатель | Значение |
|------------|---------:|
| строк в сводке | 18 808 |
| строк в факте | 112 650 |
| схлопывание | 6.0× |
| оборот сводки | **13 221 498.11 BRL** |
| оборот факта | **13 221 498.11 BRL** |
| расхождение | **0.00** |

Сводка наполняется **двумя путями**, и оба воспроизводимы:

1. **materialized view** `mv_gmv_day_category_mv` — срабатывает на вставку
   в `fact_sales` (проверено экспериментом, см. ниже);
2. **явная пересборка** `TRUNCATE` + `INSERT ... SELECT` — так сводка
   приводится в порядок после полного refresh факта.

## Как запустить

Данные в ClickHouse уже есть (З07). Сводка создаётся и пересобирается так:

```bash
# DDL + пересборка + сверка с фактом
python 09_З09_mv_витрина/etl/build_mv.py

# то же, но пересобрать дважды и доказать идемпотентность
python 09_З09_mv_витрина/etl/build_mv.py --rebuild-twice

# доказать, что materialized view действительно срабатывает
python 09_З09_mv_витрина/etl/check_mv_fires.py
```

Сохранить протокол:

```bash
python 09_З09_mv_витрина/etl/build_mv.py --rebuild-twice --out 09_З09_mv_витрина/evidence/mv_checks_raw.txt
```

> `check_mv_fires.py` **пишет в базу** две синтетические строки
> (`order_id = '__MV_TEST__'`, дата 1999-01-01) и сам их удаляет.
> В конце он сверяет базовые числа и падает, если что-то осталось.

## Как пересчитать сводку после повторной загрузки

Порядок жёсткий:

```text
python 07_З07_загрузка_clickhouse/etl/load_clickhouse.py   # факт обновлён
python 09_З09_mv_витрина/etl/build_mv.py                   # сводка пересобрана
```

**Почему мало одной view.** Загрузка факта — полный refresh
(`TRUNCATE` + `INSERT`). View реагирует на каждую вставку и не знает про
удаление: после перезагрузки в сводке лежали бы и старые, и новые строки.
`build_mv.py` начинается с `TRUNCATE`, поэтому результат не зависит от
того, сколько раз грузили.

## Что лежит в строке сводки

| Колонка | Тип | Определение |
|---------|-----|-------------|
| `order_date_key` | `Date` | день покупки |
| `category_name_pt` | `LowCardinality(String)` | категория товара |
| `gmv_brl` | `SimpleAggregateFunction(sum, Decimal(38,2))` | `SUM(amount)` по `delivered` |
| `freight_brl` | `SimpleAggregateFunction(sum, Decimal(38,2))` | `SUM(freight_value)` |
| `qty` | `SimpleAggregateFunction(sum, UInt64)` | `SUM(qty)` |
| `positions` | `SimpleAggregateFunction(sum, UInt64)` | `COUNT(*)` строк факта |

**`orders` в сводке нет осознанно:** заказ может содержать позиции разных
категорий, поэтому `COUNT(DISTINCT order_id)` по строкам сводки не
складывается. Подробно — в [`notes/z09.md` §3](notes/z09.md).

## Что показал эксперимент с view

| Вопрос | Ответ |
|--------|-------|
| View реагирует на `INSERT` в факт? | **да** — строка `1999-01-01 × __mv_test__` появилась в сводке сама |
| View реагирует на `DELETE` из факта? | **нет** — строку из сводки пришлось удалять вручную |
| После удаления числа вернулись? | **да** — 112 650 / 18 808 / 13 221 498.11 |
