## Как запустить

```bash
pip install duckdb

# пересобрать витрину с нуля
python 03_З03_витрина_duckdb/etl/build_duckdb.py

# пересобрать и сразу прогнать проверки
python 03_З03_витрина_duckdb/etl/build_duckdb.py --checks

# только вывод проверочных запросов (база уже собрана)
python 03_З03_витрина_duckdb/etl/run_checks.py
```

> **Про «вывод проверочных запросов».** Файл `sql/checks_duckdb.sql` содержит
> восемь отдельных проверок. Выполнить его «одним куском» и увидеть все
> результаты нельзя: `con.execute()` с многооператорным текстом выполняет
> все запросы, но **возвращает только результат последнего** и ничего
> не печатает. Поэтому `etl/run_checks.py` разбирает файл на запросы и
> выполняет их по одному — с заголовком и примечанием из самого SQL.
>
> Сделать это можно и руками: открыть `data/warehouse.duckdb` в любом
> SQL-клиенте и выполнить каждый `SELECT` по отдельности.
>
> Сохранить вывод в evidence:
> ```bash
> python 03_З03_витрина_duckdb/etl/run_checks.py --out evidence/checks_raw.txt
> ```

Сырьё берётся из `data/raw/` .
Если папка другая — задайте переменную окружения `RAW_DIR`.

Открыть готовую базу:

```bash
python -c "import duckdb; duckdb.connect('data/warehouse.duckdb').execute('SHOW TABLES').fetchall()"
```

## Способ загрузки

Не «я нажал в DBeaver», а три шага, которые запускаются одним скриптом
`etl/build_duckdb.py`:

| Шаг | Файл | Что делает |
|-----|------|-----------|
| 1 | `sql/ddl_duckdb.sql` | создаёт таблицы с **явно объявленными типами** |
| 2 | `sql/load_duckdb.sql` | `DELETE FROM` по всем таблицам, затем `INSERT … SELECT` из CSV |
| 3 | `sql/checks_duckdb.sql` | проверки из п.3 задания (с `--checks`) |

Порядок внутри шага 2: **справочники → факт**. Факт джойнит `dim_product`
за `category_name_pt`, поэтому таблица должна быть готова первой.

Плейсхолдер `{RAW}` в SQL подставляет скрипт — в самих SQL-файлах путь к
сырью не зашит, поэтому их можно перенести в другой проект.

Колонки вставки в факт перечислены **явно** (`INSERT INTO fact_sales (… )`),
а не позиционно: иначе добавление меры (например `qty`) молча сдвинуло бы
все колонки вставки.

## Повторная загрузка (чтобы не было удвоенных продаж)

> **Стратегия — полный refresh.** Каждый запуск сначала делает
> `DELETE FROM` по всем семи таблицам, потом заливает заново.
> Второй прогон даёт ровно тот же результат, а не вдвое больше строк.

Это осознанный выбор: витрина — 112 650 строк, полная перезагрузка занимает
секунды. Инкремент по дате здесь дороже и сложнее, а на больших данных
(см. [`cut.md` §7](../02_З02_паспорт_star/cut.md)) придётся перейти на него.

DDL написан через `CREATE OR REPLACE TABLE`, а не `IF NOT EXISTS`.
Причина — практическая: `IF NOT EXISTS` при изменении схемы оставляет
старую таблицу как есть, и правка DDL «не применится», а падать будет
позже и совсем в другом месте (ровно этот сценарий разбирается на
[З07](../07_З07_загрузка_clickhouse/ОТЧЕТ_ПОЧЕМУ.md)). Здесь витрина
пересобирается за секунды, миграции не нужны.

## Ключевые решения (коротко)

| Решение | Почему |
|---------|--------|
| деньги — `DECIMAL(12,2)` | в сырье приходят как `DOUBLE`; на З11 SQL и дашборд разъедутся на копейки |
| **`amount` вместо `price`, добавлена `qty`** | имена мер приведены к образцу звезды из раздатки (`star_retail.md`): `amount` — аддитивная сумма, `qty` — число штук. В Olist количество всегда 1, поэтому `qty = 1`, а `unit_price` не заводится — обоснование в [паспорте §4](../02_З02_паспорт_star/passport.md) |
| `payment_value_order` лежит в факте, но **не суммируется** | платёж один на заказ, а строка — на позицию. Подробно в паспорте §4 |
| `dim_geo` схлопнут агрегатом | иначе `LEFT JOIN` по префиксу размножит строки факта |
| `nao_categorizado` вместо `NULL` | 610 товаров не должны исчезать из отчёта по категориям. Эта категория добавлена и в `dim_category` — иначе строки факта оказались бы сиротами |
| `dim_date` генерируется, не берётся из файла | календаря в сырье нет |
| категория денормализована в факт | срез «оборот по категориям» без джойна к версиям SCD2 |
