| Условия («Период с») | SQL | Сводка | Карточка | Дашборд |
|----------------------|----:|-------:|---------:|---------:|

Предусловия: ClickHouse с данными (З07), сводка (З09), дашборд (З10).



## Условия сверки — коротко

| Параметр | Значение |
|----------|----------|
| База | ClickHouse `olist` (не DuckDB) |
| Метрика | `GMV_delivered` — `SUM(amount)` по `delivered` |
| Фильтр | «Период с» (`date/single`), одинаковый слева и справа |
| Регион / магазин | не фильтруем: на карточке такого фильтра нет |
| Точек проверки | 3 (2016-09-04, 2017-01-01, 2018-01-01) |

Подробно — в [`notes/sverka.md` §1](notes/sverka.md).

## Четыре источника одного числа

| | Что | Как получено |
|---|-----|--------------|
| **A** | эталонный SQL | `canonical_metric.sql` + условие по периоду, ClickHouse |
| **S** | сводка З09 | `sum(gmv_brl)` из `mv_gmv_day_category` |
| **B** | карточка | `POST /api/card/{id}/query` — тот же запрос, что у карточки |
| **D** | дашборд | `POST /api/dashboard/{d}/dashcard/{dc}/card/{id}/query` — путь UI |

**S** добавлено специально: это проверка причины «виджет смотрит в другую
таблицу». Если бы сводка считала иначе, это всплыло бы здесь, а не на экране
у преподавателя.

## Почему не пришлось «искать и устранять расхождение»

Задание предполагает, что расхождение может быть. Здесь его нет — и это
не везение, а следствие решений на предыдущих шагах:

| Причина из задания | Чем закрыта |
|--------------------|-------------|
| скрытый фильтр | у дашборда ровно один параметр, он задан явно в протоколе |
| другая таблица / другая формула | столбец S: сводка = факт |
| деньги во `FLOAT` | `Decimal` на всех слоях; `Float64` только для безразмерных долей |
| подпись ≠ SQL | текст карточки сверяется с файлом автоматически |

Разбор по каждой причине — в [`notes/sverka.md` §4](notes/sverka.md).
