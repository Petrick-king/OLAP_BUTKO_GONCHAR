# Почему именно такой `ORDER BY`

Задание З07 просит коротко (3–5 предложений) обосновать порядок хранения.
Ниже — обоснование и сам порядок.

> Правило, которое это подтверждает, прямо из раздаточных материалов
> ([`FAQ_Дисциплины.md`](../раздаточные%20материалы/FAQ_Дисциплины.md)):
> **«ORDER BY в CH = уникальность? Нет. Это ключ сортировки/пропуска блоков.»**

---

## Что стоит в `fact_sales`

```sql
ENGINE = MergeTree
PARTITION BY toYYYYMM(order_date_key)
ORDER BY (order_date_key, order_status, seller_id, category_name_pt,
          customer_id, product_id, order_id, order_item_id);
```

---

## Обоснование

**1. `order_date_key` — первым, потому что дата есть в `WHERE` каждого
запроса из паспорта.** Все три вопроса З04 начинаются с отрезка дат
(2017 год, 2018 год, помесячно), и главная метрика тоже считается
за весь период. Дата — самая селективная из колонок фильтра
(774 значения на 112 650 строк), поэтому с неё начинается префикс
разреженного индекса, и ClickHouse может не читать целые блоки.

**2. `order_status` — вторым, потому что он есть в определении самой метрики.**
`GMV_delivered` = `SUM(price) WHERE order_status = 'delivered'`, то есть
**каждый** запрос по этой витрине фильтрует статус. Колонка с 8
значениями стоит в префиксе рядом с датой: сузив диапазон дат,
ClickHouse отсекает ещё и заведомо отменённые/недоступные заказы.

**3. Дальше идут ключи джойнов в порядке «как часто фильтруют»:**
`seller_id` (вопрос 1 — регион продавца), `category_name_pt`
(вопрос 2 — доли категорий; денормализовано в факт именно поэтому),
`customer_id` (вопрос 4 — регион покупателя), `product_id` (точечные
срезы по товару).

**4. `order_id, order_item_id` в конце — это зерно строки.**
Они стоят последними сознательно: они нужны не для фильтра, а для
уникальной идентификации строки при отладке и сверке. Их в префиксе
индекса делать незачем.

**5. `PARTITION BY toYYYYMM(order_date_key)` — не про скорость.**
112 650 строк разбиваются на 25 месячных партиций: для такого объёма
это не ускорение, а задел на рост. Партиция нужна, чтобы можно было
дёшево удалять старые данные (`TTL`) и не сканировать лишнее при
запросах без фильтра по дате.

---

## Чего `ORDER BY` **не** делает

> **`ORDER BY` — это НЕ уникальный ключ.**

В ClickHouse нет ограничения уникальности. Две строки с одинаковым
набором значений в `ORDER BY` **не запрещены** и **не схлопываются**.
`ORDER BY` задаёт физический порядок строк на диске и работает
как префикс разреженного индекса — не более того.

Если нужна дедупликация, это **отдельный движок**:

| Таблица | Движок | Почему |
|---------|--------|--------|
| `fact_sales` | `MergeTree` | факт не должен схлопываться: повтор строки = задвоение продаж, и лучше пусть оно будет видно, чем тихо исчезнет |
| `dim_product_scd2` | `ReplacingMergeTree(valid_to)` | справочник с версиями: повторная загрузка той же версии схлопывается, остаётся строка с бОльшим `valid_to`, то есть более поздняя |
| остальные `dim_*` | `ReplacingMergeTree` | маленькие справочники, повтор безвреден, а `ORDER BY` по ключу делает их заодно дедуплицируемыми |

**Важная оговорка про `ReplacingMergeTree`.** Схлопывание происходит
при **слиянии частей**, а это асинхронная операция. Сразу после повторной
загрузки дубли ещё могут быть видны — их убирает либо `OPTIMIZE TABLE …
FINAL`, либо суффикс `FINAL` в запросе. Поэтому `load_clickhouse.py`
после загрузки зовёт `OPTIMIZE TABLE olist.dim_product_scd2 FINAL`.

## Проверка: данные действительно лежат по датам

```sql
SELECT partition, name, active_rows
FROM system.parts
WHERE database = 'olist' AND table = 'fact_sales' AND active
ORDER BY partition
LIMIT 30;
```

Партиции идут по месяцам, а внутри каждой `ORDER BY` начинается с
`order_date_key` — то есть физический порядок строк действительно
совпадает с логическим. Именно это и нужно для data skipping:
запрос «2017 год» не читает части за 2018-й.
